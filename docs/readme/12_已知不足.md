## 评估

- 语料是项目自述（98 篇笔记/面试题/踩坑故事），测试集也由这些 chunk 生成；多金标只能修正“同一答案在别的文档”，不能消除“自己考自己”的外部效度问题。
- v3 已加 `evidence_chunk_ids` 和近重复多金标（`gold_chunk_ids` / `gold_sources`），但仍不是人工标注的真实用户查询集。
- source 级和 chunk 级指标要同时报告：source 任意块命中会高估，单金标会低估；两者都不能单独代表真实能力。
- 阈值 `MAX_DISTANCE=0.96` 是检索层接受率，不是端到端幻觉率；负样本误接受率（FPR）和 `1 - precision`（FDR）不要混用。
- 阈值只 gate 检索，不 gate 生成：检索为空时工具返回一句“没有找到”，Agent 仍可能继续生成。真正的拒答需要在 graph 层做分支。
- 阈值用向量 top-1，且在 BM25/RRF 之前判断；BM25 能命中但向量距离大的 query 会被提前拒绝。
- 端到端评估是直接 RAG 链路（检索 + 生成 + judge），不覆盖 MCP 工具选择、多轮改写和 Agent 循环。
- LLM-as-judge 默认与回答模型同为 DeepSeek，存在自评偏好；可通过 `JUDGE_*` 环境变量换模型，并人工抽查校准。

## 服务与工程

- pymysql 是**同步客户端**，在 async 路径上会阻塞事件循环（生产应换 `aiomysql`）
- `save_conversation` 每次请求新建 MySQL 连接，无连接池
- 流式状态机用布尔变量表达，边界情况可能出错，且没有自动化测试覆盖
- 依赖只有下界、没有 lockfile；本机曾出现 torch 安装残缺，说明干净环境复现仍需验证
- 集成测试需要本地 HF 模型，CI 只跑单元测试
