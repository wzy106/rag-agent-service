# 十五、项目新增数据（更新）

### 性能修复（2026-10-16）

**问题**：文档里写的"MCP Server 常驻""单次请求 2~3 秒""Rerank 单次 50~100 ms"**从未实测**，与代码实际行为不符。

**实测（本机 CPU，负载波动大，数值受机器影响）**：
- `client.get_tools()` 是**每次工具调用新建 session** → 重新 spawn `mcp_rag_server.py` 子进程 + 重载全部模型：**第 1 次 44.1s / 第 2 次 35.2s**。
- 进程内拆解单次检索：embed 9ms、向量检索 15ms、BM25 <1ms，**Rerank 占绝对大头**（20 候选，负载高时实测 13.2s，空闲时约 2~7s）。

**修复**：
1. MCP 改**常驻 session**（`client.session()` + `load_mcp_tools`）→ 每调用 **44s/35s → 12.9s / 7.3s / 7.3s**（首次含 reranker 懒加载，后续稳定约 7s）。
2. MCP 工具改 async + `anyio.to_thread`，避免同步检索阻塞 MCP server 事件循环（否则并发调用仍串行）。
3. Rerank 配置化（**不改变默认口径**）：候选数 `RAG_RECALL_K`（默认 20）、截断长度 `RAG_RERANK_MAX_LENGTH`、精排开关 `RAG_ENABLE_RERANK`。
4. 服务启动时预热一次检索，把 reranker 加载成本前移到启动阶段。

**关于候选数的取舍**：在 v2 的 source 级口径下，把候选从 20 降到 10，精排耗时近似减半，但 Rerank 召回从 57.0% 掉到 53.8%，增益从 +4.4 塌缩到 +1.2，得不偿失——所以默认仍保留 20。v3 换成 source/chunk 双粒度 + 多金标后，具体数字见根目录 README。

**订正的数字**：Rerank 模型 3.36 GB → **约 1.1 GB（278M 参数）**；单次请求 2~3 秒 → **约 7~13 秒（warm，本机 CPU）**；Rerank 单次 50~100 ms → **约 2~7 秒（20 候选）**。

### 安全修复：`/history` 越权（2026-10-16）

**问题**：`/history` 无鉴权 + `thread_id` 有默认值 + 单共享 key → 任何人按 thread_id 就能读到别人的会话（**越权 / IDOR**）。

**修复**：
1. `/history` 加鉴权（`Depends(verify_key)`）。
2. `thread_id` 必填（去掉 `user_001` 默认值）。
3. 多 key（`API_KEYS`）→ 每个 key 一个租户；记忆按 `{租户}:{thread_id}` 隔离，历史表加 `owner` 列只查自己租户。
4. 密钥校验改 `hmac.compare_digest`（恒时比较）。

**核心认知**：**认证 ≠ 授权**——认证只证明"你是谁"，"能读哪些数据"必须在数据层按身份过滤。
