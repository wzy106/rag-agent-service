# 故事 30：Rerank 收益被语料规模压制（2026-10-11）

### 问题
为了提升检索精度，我加了两阶段检索：混合检索召回 Top-20 → Reranker（bge-reranker-base）精排 Top-3。

**预期**：精确率 0.86 → 0.92+，MRR 0.94 → 0.99+。

**实际**：精确率 0.86 → **0.90**，MRR 0.94 → **0.97**。

**提升有效，但远没到预期。**

### 分析
**Rerank 本身没问题**——它确实把更相关的文档排到了前面（精确率 +0.04，MRR +0.03）。

**问题在语料规模**：
- 只有 2 篇文档、102 个 chunk
- 每条 query 的期望 source 只有 1~2 个（甚至有些 query 期望命中两篇）
- 随机基线召回率 84.1%——意味着"瞎抽 3 个"就已经命中 84%
- **真实判别空间只有 15.9 个点**

**当语料小时，天花板效应很明显**：
- 混合检索已经能拿到大部分正样本（96.7% 召回）
- Reranker 能优化的空间就那么大——它只能在"已经召回的 20 条里"重排
- 如果这 20 条里真正相关的只有 1~2 条，Reranker 再准也只能把其中 1 条排到 Top-1，另外 2 个位置还是会被不太相关的占据

**类比**：考试范围只有 10 页书，满分 100 分。你从 80 分提到 90 分，已经接近天花板了——不可能再提到 98。

### 方案
**短期（已完成）**：
- 加了 Reranker，精确率 0.86 → 0.90
- 用 `recall_k=20, final_k=3` 的两阶段 pipeline
- 懒加载设计（第一次调用才加载 3.36 GB 模型，不拖慢服务启动）

**长期（待做）**：
- **扩语料到 500+ chunk**：这是唯一的根治方案
- 用公开中文技术文档（LangChain / LangGraph / FastAPI 官方文档的精华部分）
- 或者把现有的 `docs/` 从 2 篇扩到 20 篇
- 只有语料大了，Rerank 才能发挥全部威力

### 效果对比

| 策略 | 召回率 | 精确率 | MRR | 多样性 |
|---|---|---|---|---|
| 混合检索 | 96.7% | 0.86 | 0.94 | 1.30 |
| **混合检索 + Rerank** | 96.7% | **0.90** | **0.97** | 1.17 |

**观察**：
- 精确率和 MRR 都涨了（**Rerank 生效**）
- 召回率不变（Rerank 只重排，不召回）
- 多样性略降（1.30 → 1.17）—— Reranker 偏向最相关的，牺牲了多样性——**符合预期**

### 收获
**Rerank 是完整 RAG pipeline 的最后一块拼图。** 召回 → 融合 → 精排，缺了精排就像"做菜没上调料"。

**但精排的收益被语料规模约束**：
- 语料小 → 天花板低 → Rerank 可优化空间小
- 语料大 → 天花板高 → Rerank 才能真正发挥作用
- **再好的精排也救不了小语料**

**面试时要主动说这个局限。** 这比"我加了 Rerank，精确率提升很大"更可信——**面试官会觉得你知道自己在说什么**。

**面试时能讲**：
> "我加了两阶段检索：混合检索召回 Top-20，用 bge-reranker-base 交叉编码器精排 Top-3。精确率从 0.86 提到 0.90，MRR 从 0.94 提到 0.97。Reranker 是懒加载的——第一次调用才加载 3.36 GB 模型，不拖慢服务启动。但这里有个诚实的局限：Rerank 收益被语料规模压制，只有 2 文档 102 chunk，判别空间只有 15.9 个点，天花板效应明显。下一步扩到 500+ chunk 才能发挥全部威力。"
